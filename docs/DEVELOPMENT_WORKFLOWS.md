# 개발 방식 라이브러리와 프로젝트 기억

## 참고 프로젝트 확인

사용자가 보낸 영상 캡처의 **Everything Claude Code**는 현재 [affaan-m/ECC](https://github.com/affaan-m/ECC)로 연결됩니다.
2026-11-13 GitHub API 조회 시 별 302,183개를 확인했습니다. 숫자는 조회 시점의 값입니다.
참고한 checkout은 `d2ef2680594f9a17526a6e1a2e18b3d242c5d17b`입니다.

ECC는 전문 에이전트, 재사용 가능한 개발 스킬, 규칙, 훅, 기억과 문맥 관리를 묶는 프로젝트입니다.
공식 README, planner/code-reviewer, TDD와 verification 문서를 참고했습니다. 라이선스는 MIT, 원저작자는 Affaan Mustafa입니다.
이번 구현은 그 구조를 참고해 AI DEV DIRECTOR용으로 작성했습니다. 외부 문서에 담긴 설치·실행 지시는 참고 자료로 다뤘습니다.
개발자가 직접 읽은 외부 저장소는 배포 ZIP에 포함하지 않습니다.

| 참고한 구조 | 이번 프로그램에 적용한 기능 |
| --- | --- |
| 작업별 재사용 스킬 | 작업에 맞는 7개 기본 개발 방식 |
| 전문 역할 분담 | HEAD·BUILDER·REVIEWER에 전달하는 방식별 지침 |
| 세션/프로젝트 기억 | 같은 프로젝트의 검증 완료 기록 최대 3건 참조 |
| 문맥 최적화 | 파일 이름·설정 파일 신호를 제한된 범위에서 수집 |
| 실행 전후 연결 | 시작/재계획 시 지침과 참고 기록을 연결하고 기존 실행 검증을 사용 |

이 기능은 프로그램 내부의 개발 절차입니다. Claude/Codex의 글로벌 설정, MCP 서버, 외부 플러그인이나 실행 훅을 설치하는 기능은 포함하지 않습니다.

## 사용 방법

1. 미션 센터의 **작업에 맞는 개발 방식** 카드 또는 **전체 방식 보기**를 엽니다.
2. 방식을 고르면 기존 초안에 해당 방식이 선택됩니다. 이때 작업은 실행되지 않습니다.
3. 목표·완료 조건·규모와 함께 선택한 방식의 지침을 확인합니다.
4. **같은 프로젝트의 검증된 작업 기록 참고**를 켜거나 끌 수 있습니다.
5. **참고 가능한 프로젝트 기록 보기**에서 실제 참고 후보와 프로젝트 문맥 수집 상태를 확인합니다.
6. **미션 시작**으로 실행합니다. 선택한 방식과 기록 사용 여부는 시작 요청에 고정되며 중복 방지에도 반영됩니다.
7. 미션 상세와 보고서에서 요청한 개발 방식과 실제로 참고한 기록 ID를 확인할 수 있습니다.

**스테이지에서 확인**도 선택한 방식을 전달합니다. `[빠르게] [버그 진단] ...`처럼 읽을 수 있는 태그를 사용하며,
기록 참고를 끄면 `[기록 제외]`가 함께 전달됩니다. 태그는 HEAD에 요청을 넘기기 전에 해석합니다.
예전 방식으로 작성된 일반 채팅과 CLI 요청은 기존 동작을 유지합니다.

## 방식별 의도

| 방식 | 계획·구현·검수에서 중점적으로 다룰 내용 |
| --- | --- |
| 자동 선택 | 목표의 첫 문단에서 관련 표현을 찾아 기본 방식을 고름 |
| 게임 개발 | 엔진 버전·작은 플레이 루프·씬/에셋 연결·실제 엔진 테스트 |
| 기능 개발 | 동작 정의, 작은 구현, 정상·예외 상황 검증 |
| 버그 진단 | 재현 조건, 원인 수정, 회귀 테스트 |
| 테스트 중심 | 동작 테스트의 선행 설계, 경계/실패 상황, 검증 근거 구분 |
| 보안 개선 | 입력과 권한 경계, 방어적 수정, 거부 동작 검증 |
| 구조 개선 | 유지할 외부 동작, 작은 구조 변경, 호환성 검수 |

지침을 모델에게 전달하는 기능입니다. 체크리스트를 완료했다고 자동 판정하지 않습니다.
특히 테스트 중심 방식이 RED/GREEN 단계의 실행을 자동 보장하거나 테스트 커버리지 수치를 인증하지 않습니다.
실제 통과 여부는 기존 Verifier의 실행 기록과 독립 검수 결과를 확인합니다.
새 지침은 `allowed_paths`, `protected_paths`, 파일/diff 상한, 위험도나 승인 요구를 변경하지 않습니다.

## 프로젝트 기억의 조건

다음 조건을 모두 충족한 기록만 자동 참조 후보가 됩니다.

- 정규화된 프로젝트 경로가 현재 프로젝트와 같음.
- 미션 상태가 `DONE`.
- 마지막 단계가 `PASS`, 독립 검수도 `pass`.
- 실제 테스트 수가 1개 이상이며 전체 통과, 실패 0개.

최근 최대 3건의 목표(최대 240자), 요약(최대 600자), 테스트·검수와 원본 적용 상태를 구조화해 전달합니다.
과거 실행 결과는 참고 자료이며 새 지시나 권한으로 취급하지 않도록 명시합니다.
원본 반영 여부도 함께 전달하므로 과거 기록과 현재 파일 상태를 구분해 확인할 수 있습니다.
실패한 시도, 검수나 테스트가 없는 완료 기록, 다른 프로젝트의 기록은 자동 참조에 포함하지 않습니다.
새로운 교훈이나 스킬을 임의로 생성해 저장하는 자기 학습 기능은 포함하지 않습니다.

초기 계획과 다음 단계 재계획에 같은 방식을 전달합니다. `memory_sources`/`planning_memory_sources`에는 실제 전달한 기록 ID가 남습니다.
프로젝트 기억 사용을 끄면 과거 미션 요약을 조회해 HEAD 문맥에 넣지 않습니다.

## 문맥 탐색

기존 코드는 파일 수를 마지막에 잘라내기 전에 프로젝트의 많은 폴더를 순회했습니다.
새 탐색기는 `scandir`로 항목을 읽으면서 다음 기본 상한을 적용합니다.

- 파일 이름 목록: 최대 100개.
- 방문 폴더: 최대 120개.
- 살펴보는 항목: 최대 3,000개.
- 주요 신호: `pyproject.toml`, `package.json`, `go.mod` 등 고정된 설정 파일의 존재 여부.

`node_modules`, 가상환경, 캐시·빌드 산출물, 민감한 설정 폴더와 심볼릭 링크는 탐색에서 제외합니다.
일반 소스·테스트와 `.github`, `.gitignore` 같은 프로젝트 설정 이름은 유지합니다.
이 단계는 파일 내용을 읽거나 패키지 설치·프로젝트 스크립트·자동 검증 명령을 실행하지 않습니다.
빌드/테스트 명령의 선택과 권한은 기존 설정 및 검증기를 사용합니다. 수집 상한 도달 여부는 UI에서 확인할 수 있습니다.
실제 토큰 절감률은 측정하지 않았으며 임의의 절감 수치를 표시하지 않습니다.

## 호환성과 검증

시작 요청에 `workflow_id`와 `use_project_memory`를 추가했습니다. 기존 2차 개선판의 접수 기록은 기본값으로 정규화해 비교하므로
같은 요청이 재실행되지 않습니다. 방식 또는 기록 사용 옵션이 달라진 같은 ID의 재전송은 내용 충돌로 거부합니다.
기존 미션에 방식 메타데이터가 없으면 해당 방식이 적용되었다고 표시하지 않습니다.

주요 구현은 `core/workflows.py`, `core/project_context.py`, `core/mission.py`와 미션 센터 UI입니다.
새 읽기 API는 `/ops/workflows`, `/ops/project-memory`이며 기존 로컬 출처 검사를 사용합니다.

검증 명령:

```sh
python -m pytest -q tests/test_development_workflows.py
DIRECTOR_UI_PYTHON=.venv/bin/python DIRECTOR_UI_CHROMIUM=/usr/bin/chromium node tests/browser/execution_center.cjs
```

테스트는 범위·승인 조건 보존, 다음 마일스톤으로의 지침 유지, 검증 기록 필터·격리·상한·사용 제외,
문맥 탐색 상한과 링크/의존성 제외, 이전 접수 기록의 중복 방지, 스테이지 태그 전달을 확인합니다.
브라우저에서는 방식 선택만으로 실행되지 않는 점, 초안 복원, 기록 미리보기와 제외, 시작 요청/상세에 선택이 유지되는 점도 확인합니다.
상세 결과는 [검증 기록](VALIDATION_MISSION_CENTER.md)에 정리합니다.
